# api-gateway

**Responsibility:** Single external entry point: JWT validation, tenant
resolution, request routing to internal gRPC services, WebSocket upgrade
proxying for Agent Desktop. Described in the architecture doc as
"supporting, not a domain service" (Section 2.2) — it fronts Task Router
and Tenant & Identity Management rather than owning a bounded context
itself.

**State:** Stateless (the ws-ticket signing keypair is held only in
memory and regenerated on every restart — see `internal/wsticket`).

**Status:** real implementation — REST routing (via
[grpc-gateway](https://github.com/grpc-ecosystem/grpc-gateway)), end-user
JWT validation, and WebSocket upgrade proxying for browser-based Agent
Desktop clients.

## Out of scope for this pass

TLS termination, rate limiting, quota enforcement, and feature-flagging
are documented as this layer's eventual job (architecture doc Section
1.1) but are **not** implemented here — this milestone is JWT validation +
routing + WebSocket proxying only. `ingress-nginx`/`mkcert` TLS remain
deferred per architecture doc Section 1.4; this service's K8s `Service` is
`ClusterIP` like every other service today (see
`deploy/k8s/api-gateway/service.yaml`'s comment).

## REST surface

Generated by `protoc-gen-grpc-gateway` from `google.api.http` annotations
added directly to the RPCs in `proto/task-router/v1/task_router.proto`,
`task_router_admin.proto`, and `proto/tenant-identity/v1/tenant_identity.proto`
(one source of truth per RPC — see `proto/buf.gen.yaml`). Full route table:
`ARCHITECTURE_FLOW.md`.

`IssueServiceToken` deliberately has **no** REST annotation — it is a
service-to-service mechanism, never meant to be reachable from outside the
cluster, so it simply never appears on this gateway's HTTP surface.

## Authentication

- **REST:** every route except `POST /v1/auth/login`, `POST /v1/tenants`
  (CreateTenant), `GET /v1/tenants`/`GET /v1/tenants/{id}` (ListTenants/
  GetTenant — platform registry reads), and `POST /v1/tenants/{id}/users`
  (CreateUser) requires `Authorization: Bearer <jwt>`, verified against
  Tenant & Identity's signing public key (`internal/gwauth`). A valid
  token is forwarded to the backend unmodified — grpc-gateway forwards the
  `Authorization` header to outgoing gRPC metadata automatically (see
  `internal/gwauth`'s package doc comment) — so the backend's own
  `pkg/tenantctx` interceptor re-verifies it independently (Layer 2
  defense in depth, architecture doc Section 1.1).
- **WebSocket ticket:** `POST /v1/ws-ticket` (itself requiring a normal
  valid bearer token) mints a short-lived (default 45s) single-purpose
  ticket, signed by this service's OWN dedicated ECDSA keypair —
  deliberately **not** the same key as Tenant & Identity's session-signing
  key, since API Gateway never holds that private key. See
  `internal/wsticket`'s package doc comment for the full "why a separate
  key" and "short TTL, not true single-use" scoping rationale (the honest
  tradeoff: a leaked ticket could in principle be replayed within its
  ~45s window — no server-side used-ticket registry exists in this
  milestone).

## WebSocket proxying

`GET /ws?ticket=<jwt>` is **proxied** (not redirected) to Agent & Presence
Service's own `/ws` endpoint — see `internal/wsproxy`'s package doc
comment for the full proxy-vs-redirect design discussion. Summary: proxying
keeps API Gateway as the genuinely single external entry point (matching
architecture doc Section 2.2's description and Section 2.1's service map),
at the cost of this service holding one open upstream connection per
active WebSocket client for the connection's lifetime (a standard,
accepted reverse-proxy tradeoff at this system's scale).

Agent Presence's `/ws` endpoint accepts the SAME ticket as a `?ticket=`
query parameter directly too (see
`services/agent-presence/internal/wsserver`'s doc comment) — proxying
through this gateway is the architecturally intended path for a real
external client, but is not the only way Agent Presence's endpoint can be
reached in this dev topology.

## Backend addressing

Dials Task Router and Tenant & Identity via in-cluster Kubernetes Service
DNS names (`task-router-svc:50054`, `tenant-identity-svc:50051`), sourced
from env vars (`TASK_ROUTER_GRPC_ADDR`, `TENANT_IDENTITY_GRPC_ADDR`) — see
`cmd/main.go`. `localhost` defaults exist only for standalone `go run`
outside the cluster (CLAUDE.md Rule 2); every K8s deployment.yaml supplies
a real override.
